# CHARM-IIからKarqriへ――RTOSの動きを見えるようにする

Karqriの出発点は、私が1986年に開発に携わっていたRTOS、CHARM-IIにある。

約40年後の2026年、残っていたソースコードや資料を読み直し、当時の仕組みを現代の環境で確かめる作業を始めた。最初は過去の実装を調べ直すつもりだったが、POSIX環境やRaspberry Pi Picoで実験を重ねるうちに、新しいRTOSを作る方向へと発展していった。それがKarqriだ。

ただし、KarqriはCHARM-IIをそのまま移植したものではない。1986年の設計思想、2026年に行った復元・研究、そして新しく作った実装が、段階を経てつながっている。

## 1. 1986年、CHARM-IIを開発していた頃

1986年、私はMotorola MC68000系のCPUを対象とするRTOS、CHARM-IIの開発に携わっていた。開発や検証にはSUN-2ワークステーションとWhitesmiths Cを使っていた。SUN-2のCPUは68010で、対象の68000とは異なる部分もあるが、同じ系列の命令体系を利用できた。

CHARM-IIには、優先度に基づくタスクの選択、Ready列、Eventによる待ちと起床、Timerなどの仕組みがあった。タスクの状態を複数のbitの組合せで表し、例えばEvent待ちと実行停止を同時に保持できる設計も、その特徴の一つだった。

当時はVRTXやpSOSの仕様も参考にしていた。ただ、個々の設計判断について、当時の考えをすべて正確に覚えているわけではない。残されたコードから読み取れることと、現在の記憶に基づくことは分けて考えたい。

CPUに依存する部分も大きかった。コンテキスト切り替えには68000系のレジスタや例外時のスタックフレーム、例外復帰の仕組みが関わる。Cで書かれたタスク管理と、アセンブリで書かれたCPU依存処理が組み合わさって動いていた。

この頃、複数のタスクがトラックを周回するデモも作った。現在そのデモのソースコードは残っていないが、タスクの動きを画面上で見せていたことは覚えている。この記憶は、40年後の実験につながることになる。

## 2. 40年後、ソースコードを再び読み始める

2026年、残っていたCHARM-IIのソースのリストや関連資料を、改めて読み直すことにした。紙から読み取ったコードを現代の環境へ持ち込み、動作を確かめていく作業だった。

ここでAIが大いに役立った。OCRによる文字の読み取り、コードの解析、修正案の検討、テストの作成など、40年前なら手間のかかった作業を短いサイクルで進められるようになった。

一方で、OCRやAIの出力をそのまま信用できないことも分かった。記号や型の読み違いだけでなく、元のコードの意味が変わってしまう場合もある。コンパイルが通ったからといって、1986年の実装を正しく復元できたとは限らない。原資料との照合や、小さな単位での動作確認が欠かせなかった。

古いCコードを現在のコンパイラで扱うこと自体にも難しさがある。ポインタの幅、関数の呼出し規約、スタックの構成など、当時のCPUや開発環境を前提にしていた部分は、そのままでは成立しない。

このため、当時のソースを復元して調べる作業と、理解した動作を現代の環境で再現する作業は、意識して区別するようにした。

## 3. 復元から、新しいRTOSの開発へ

2026年の研究では、まずPOSIX環境でQueueやScheduler、タスクの待ちと起床などを検証した。6つのタスクがトラックを動くデモも、1986年に作ったものの記憶を手掛かりに再実装した。これは当時のデモのソースや画面を忠実に復元したものではなく、覚えている発想を現代の環境で作り直したものだ。

その後、Raspberry Pi Picoでも実験を進めた。PicoのRP2040はARM Cortex-M0+を搭載しているため、68000用のアセンブリをそのまま利用することはできない。SVCやPendSV、例外フレームなど、Cortex-Mの仕組みに合わせたコンテキスト切り替え処理を新しく設計した。この部分はChatGPTと相談しながら設計し、Codexを使って実装を進めた。

こうした実験を続けるうちに、歴史的なCHARM-IIを調べることと、現代のRTOSとして使いやすい構成を考えることが、少しずつ別の課題になってきた。そこで、2026年後半に新しいコードベースとしてKarqriを立ち上げた。

Karqriでは、Kernelの論理的な処理と、CPUや実行環境に依存するportを分けている。POSIXとPicoで共通のworkloadを動かし、タスクの進行、待ちと起床、共有領域の扱いなどを比較できるようにした。Queue、Task、Scheduler、Event、TimerなどのAPIも、現代の利用条件に合わせて整理している。

ただし、これは1986年のコードを別CPUへ単純に移したものではない一方、2026年の研究版と無関係に一から作り直したものでもない。研究版で開発したPico向けの実行基盤やデモなど、具体的な実装と知見を引き継ぎながら、Karqriの構成に合わせて変更している。

当時の設計をすべて残すことにもこだわっていない。例えば、同じ優先度のReadyタスクの並び方は、KarqriではFIFOを採用した。また、旧RTOSにあったサービスをすべて実装する方針ではなく、現行のKarqriは標準のメモリアロケータを提供していない。何を受け継ぎ、何を選び直すかも、この開発の一部だと思っている。

## 4. なぜKarqriという名前にしたのか

新しいRTOSの構想を考え始めた頃から、内部の動作をもっと視覚的に表現できないかと思っていた。

タスクが動き、何かを待ち、別のタスクからの通知で再び動き出す。Timerが満了し、Schedulerが次のタスクを選ぶ。そうした動作の連鎖を、ログや数値だけではなく、目で見て理解できるものにしたかった。

もう一つ頭にあったのが、テレビ番組『ピタゴラスイッチ』のような仕掛けだった。ある動作が次の動作を引き起こし、それがまた別の動作につながっていく。RTOSの中で起きていることを、そんなふうに見せられないだろうか。

そこで浮かんだのが、日本語の「からくり」という言葉だった。機械仕掛けや巧妙な仕組みという意味も、遊び心のある表現という意味でも、考えていた方向に合っていた。

ただ、`karakuri` という綴りでは、検索すると既存のサイトが数多く見つかる。そこで少し綴りを変えて、`Karqri` と名付けた。

この名前は、RTOSの機能そのものというより、**その動きをどう見せたいか**という構想から生まれたものだ。

## 5. Karqriでこれから試したいこと

現在のKarqriには、POSIXとPicoの実行基盤、6-taskのANSIデモ、実行中の状態を記録して時系列に表示するPico向けの検証用トレースなどがある。タスクが動いている様子や、切り替えの途中で何が起きたかを、少しずつ観察できるようになってきた。

もっとも、現在のデモが、そのまま「ピタゴラスイッチ的な可視化」を実現しているわけではない。現段階では、RTOSとしての基本動作を確かめ、観測するための仕組みを整えているところだ。

また、通常のデモや検証が実機で動いたことと、割込みのあらゆるタイミングで安全性を確認できたことも別だ。Picoの通常経路では実機での動作確認が進んでいるが、特殊な割込みタイミングや競合条件など、引き続き確認が必要な項目が残っている。

今後は、タスクが動いたという結果だけでなく、**なぜ待ったのか、何が起きて再開したのか、どの仕掛けが次の動作につながったのか**を見せていきたい。異なるCPUや実行方式を、同じ題材で比べることにも興味がある。

1986年のCHARM-IIを読み直すところから始まった作業は、いつの間にか、新しいRTOSを作り、その内部の動きを表現する試みへと広がっていた。Karqriは、その途中にあるプロジェクトだ。
