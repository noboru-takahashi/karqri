# Karqri

[English](README.md) | 日本語

## Karqriとは

Karqriは、私が1986年に開発したRTOS「CHARM-II」の設計思想と、2026年に行った復元・研究の成果をもとに、新たに開発しているRTOSです。現在はPOSIX環境とRaspberry Pi Pico（RP2040）を対象に開発・検証しています。

2026年の研究版で作ったPico向けの実行基盤やデモの一部を継承し、カーネル、API、ポートの構成を整理しています。同じカーネルと共通の処理を異なる実行環境で動かし、タスクの進行、待ちと起床、コンテキストスイッチを確かめられます。

## 現在できること

| 機能 | 内容 |
| --- | --- |
| Queue | リンク情報を要素内に持つ双方向循環リスト。FIFO・LIFO操作と優先度順の挿入に対応します。メッセージキューではありません |
| Task | タスクの開始関数と引数、優先度、状態ビット、待機後に受け取る戻り値を管理します |
| Scheduler | 実行可能なタスクを優先度順に管理します。同順位はFIFO順とし、時間片による交代や一時停止・再開に対応します |
| Event | 32ビットの通知集合を扱います。指定したビットのいずれか、またはすべてが揃うのを待てます。通知回数は蓄積しません |
| Timer | 呼出し側が用意した固定数のタイマを管理し、指定したティック数の経過後にコールバックを一度呼び出します。イベント通知にも接続できます |
| POSIXポート | 単一のOSスレッド上で、`ucontext`を使ってタスクを協調実行します |
| Picoポート | 独立したPSPスタック、SVC・PendSV、ハードウェアアラームを使い、割込みを契機にタスクを切り替えます |

### 6タスクの周回デモ

POSIX版とPico版は、`demos/common/`のCコードを共有します。三つの走路をA〜Fのタスクが移動し、イベント通知と所有状態の確認によって共有領域への進入を調整します。ANSI端末にタスクの位置、ティック数、共有領域の状態などを表示し、終了時に結果を集計します。

### 検証用トレースと時系列表示

Picoの検証用ファームウェアには、協調実行の`cooperative_three_task`シナリオだけを記録する任意のトレース機能があります。Windows側のログ収集ツールでUSB CDC出力を保存し、オフラインのTrace ViewerでHTMLの時系列図を作成できます。

全タスク・全割込みを網羅する汎用的な可視化機構ではありません。コンテキスト切り替えの受渡し記録も、次のタスクが命令を実行したことを保証するものではありません。記録処理自体が実行時間や割込みのタイミングに影響する点にも注意が必要です。詳細は[トレースとログ取得の手順](tools/pico_validation/README.md)を参照してください。

## ビルドと実行

以下のコマンドは、特記がない限りリポジトリのルートで実行します。

### POSIX：テストとデモ

必要なものはC11対応のCコンパイラ、Make、`ucontext`を使用できるPOSIXホスト環境です。既存のテストやデモはWSL Ubuntu環境で実行しています。Windows上で直接実行するためのポートではなく、ほかのホスト環境での動作を一律に保証するものでもありません。

```sh
# キュー、タスク、イベント、タイマ、タイマとイベントの接続、
# スケジューラ、POSIX統合の7項目をテスト
make test

# 独立した6タスクのデモをビルド
make posix-track-demo

# ANSI端末で実行
./build/karqri_posix_track_demo
```

端末は95列×28行以上を使用してください。通常モードは実行中タスクのチェックポイントごとに25ミリ秒待ち、全体で6000論理ティックまで進みます。実行時間は約150秒に描画やスケジューリングの処理時間が加わります。待ち時間を省く高速モードもあります。

```sh
./build/karqri_posix_track_demo --fast
```

正常終了では、終了コード0と次の行を確認します。

```text
KARQRI_POSIX_TRACK_DEMO_PASS
```

終了時の集計では、A〜Fすべてのタスクの進行、共有領域の重複利用がないこと（`overlap=0`）、取得・解放数の一致、`owner=-1`、`waiters_empty=YES`、`all_finished=YES`などを確認できます。POSIX版にはスタックガードはなく、各タスクのスタック内にローカル変数が置かれていることを検査しています。

POSIX版はチェックポイントでタスクを交代させる協調実行です。Picoのハードウェアティックとは時間の進み方が異なるため、切替回数や移動回数の完全一致ではなく、タスクの進行、共有領域の扱い、正常終了を比較します。詳しくは[POSIXデモの手順](demos/posix/README.md)を参照してください。

### Pico：SDKとツールチェーンの準備

既存のビルド確認には**Pico SDK 2.3.0**を使用しています。別途、CMake、Ninja、ARM向けGNU組込みツールチェーン（C/C++コンパイラと関連ランタイム）、SDK準備用のGitが必要です。対象はRP2040を搭載したRaspberry Pi Picoで、Pico 2への対応を示すものではありません。

Pico SDK 2.3.0のソース一式を用意し、`PICO_SDK_PATH`にその場所を設定します。次の`/path/to/pico-sdk`は、自分のSDKの絶対パスに置き換えてください。

```sh
export PICO_SDK_PATH="/path/to/pico-sdk"

# USB CDCに必要なTinyUSBを含むSDKのサブモジュールを準備
# 取得・更新にはネットワーク接続が必要になる場合があります。
git -C "$PICO_SDK_PATH" submodule update --init --recursive
```

SDKはこのリポジトリに同梱していません。UF2生成に使うpicotoolもSDK側で検索され、見つからない場合はソースの取得とビルドが行われる経路があります。オフライン環境では、対応するpicotoolを事前に準備してください。新しい環境でのSDK・ツールチェーン・picotoolの導入手順全体は、既存環境でのビルド成功とは別に確認が必要です。

`ports/pico/CMakeLists.txt`は上の環境変数を読みます。環境変数の代わりにCMakeへ`-DPICO_SDK_PATH=...`を渡すこともできます。

### Pico：リリースビルド

```sh
cmake -S ports/pico -B build/pico-rp2040 -G Ninja \
    -DPICO_BOARD=pico -DCMAKE_BUILD_TYPE=Release
cmake --build build/pico-rp2040
```

独立した二つのファームウェアが生成されます。

| ファイル | 用途 |
| --- | --- |
| `build/pico-rp2040/karqri_pico_validation.uf2` | 初回起動、協調的な切り替え、イベント待機後の戻り値、一時停止・再開、割込みによるタスク切り替えの5シナリオを検証 |
| `build/pico-rp2040/karqri_pico_track_demo.uf2` | 6タスクのANSI周回デモ |

### Pico：書込みと実行

1. BOOTSELを押しながらPicoをUSB接続し、`RPI-RP2`ドライブが現れたら離します。
2. 実行したいUF2をそのドライブへコピーします。6タスクのデモには`karqri_pico_track_demo.uf2`を使ってください。
3. 再起動後のUSB CDCポートを、ANSI表示とDTR設定に対応する端末で開きます。通信速度の設定は115200を使用できます。1200ボーによるリセットは使用しません。現在のビルドではUART出力を無効にしています。
4. デモはCDC接続を最大10秒待ち、接続時はさらに250ミリ秒待って開始します。待機中にKarqriのタスクやハードウェアティックは開始しません。未接続でもタイムアウト後に開始するため、遅く接続すると固定の初期表示を取り逃すことがあります。
5. 95列×28行以上の端末で、`Critical Zone`の見出し、六つのタスク、ティック数と切替数の進行を確認します。25ミリ秒周期で6000ティックまで進み、約150秒に起動やUSB接続などの時間が加わります。

終了時には`overlap=0`、共有領域の取得・解放数の一致、`owner=-1`、`waiters_empty=YES`、`guards=intact`、全タスクの進行を確認し、次の行を確認します。無出力や途中停止をPASSと扱わないでください。

```text
KARQRI_PICO_TRACK_DEMO_PASS
```

検証用ファームウェアの成功を示す終端行は`KARQRI_PICO_VALIDATION_PASS`です。こちらは接続を待たず、起動後1.5秒の固定待機で検証を始めるため、ログ取得が遅れるとSTARTを失う可能性があります。Windowsで取得する場合は、ログ収集ツールを先に待機させてからUF2を書き込んでください。このツールは5シナリオの検証用で、制限時間の既定値は30秒です。約150秒動く周回デモの収集には使えません。

WindowsとWSL間のUF2受け渡しや操作の詳細は[Picoの手順](ports/pico/README.md)、ログ取得と時系列表示は[Windowsツールの手順](tools/pico_validation/README.md)を参照してください。実行結果を保存するときは、ソースの版と未コミット差分、ビルド設定、SDK・ツールチェーン、UF2・ELFのハッシュ値、使用した実機とログを対応付けてください。

### 任意：協調実行シナリオのトレース

```sh
cmake -S ports/pico -B build/pico-rp2040-trace -G Ninja \
    -DPICO_BOARD=pico -DCMAKE_BUILD_TYPE=Release -DKARQRI_PICO_TRACE=ON
cmake --build build/pico-rp2040-trace
```

この設定でも周回デモのトレースは無効です。検証用ファームウェアの協調3タスクシナリオだけを記録します。記録先は256件×32バイトの固定長リングバッファで、上書きや連番の上限到達を検出できます。

ログ収集ツールとTrace ViewerはPython 3.10以降を使用します。WindowsのCOMポートから実際にログを取得するときだけ`pyserial==3.5`が必要で、Viewerとオフラインテストは標準ライブラリで動作します。時系列表示にはファームウェアが記録した時刻を使い、Windowsの受信時刻をタスクの実行時刻として扱いません。検証のPASS・FAILと、トレースのCOMPLETE・INCOMPLETEは別の判定です。

## 設計と制約

カーネルはタスクの論理状態、キュー、通知、タイマを扱い、ポートがスタック、CPUコンテキスト、実際の切り替えを扱います。キュー・タスク・イベント・タイマはアプリケーション向けの基本機能で、スケジューラと接続アダプタは内部処理や実行環境との統合向けのAPIです。

- 共有するカーネルの基本機能には内部同期がありません。読取りやコールバックを含む操作全体の排他は、呼出し側やポートが行います。Picoで直接操作する場合も、ティック割込みとの同期が必要です。
- POSIXは単一の所有スレッド、Picoは同一コアの単一実行環境が対象です。POSIXの外部スレッドやシグナルハンドラからのAPI呼出し、複数インスタンスの並行実行などは対応範囲外です。Picoの割込み保護も、ほかのコアやNMI・HardFaultとの同期を保証しません。
- タスクが待機や自己停止に入るときは、別の実行可能なコンテキストを残します。再選択を抑止している間に、待機・自己停止・タスク関数からの正常復帰をしてはいけません。再選択の抑止は割込みロックではありません。
- 全タスクの正常終了と、通知元や外部からの参照がなくなったことを確認してから、コンテキストや記憶領域を破棄します。POSIXの`run()`がtrueで返るだけでは全タスクの終了を意味しません。実行中コンテキストの破棄や未終了のタスク群の再開は対応範囲外です。
- 現行カーネルは、標準メモリアロケータ、RTOSのメッセージ送受信サービス、イベント待ちのタイムアウトや途中取消し、タスクの強制削除、周期タイマを提供していません。

状態ビットの解釈、割込みマスクの保存・復元、コールバックの再入条件など、詳しい契約は[API Reference](docs/api-reference-ja.md)、[API Design Notes](docs/api-design-ja.md)、[POSIXの実行契約](ports/posix/README.md)を参照してください。

### 検証状況

これまでに、次の動作を確認しています。

- ホストテスト7項目のPASS
- POSIXデモの通常・高速モードでの6000論理ティック到達と正常終了
- Picoの通常5シナリオの実機PASS
- Picoの6タスクデモの初期画面表示、6000ティック完走、終端PASS（実機画面で確認）

特殊な割込み競合や起動・終了時の境界条件、スタック使用量などは追加検証中です。通常経路の成功が、あらゆる割込みタイミングでの安全性を示すものではありません。検証範囲と未確認事項は[API Reference](docs/api-reference-ja.md)の第19節、実装上の制約は[API Design Notes](docs/api-design-ja.md)を参照してください。

## 名前と歴史

新しいRTOSを考え始めた頃から、内部動作を可視化したいと思っていました。タスクや通知、タイマの動きを、ピタゴラスイッチのように複数の仕掛けが連鎖する表現にできないか。その構想から、日本語の「からくり」という言葉が浮かびました。

`karakuri`では既存の検索結果が多いため、識別しやすい綴りとして`Karqri`を選びました。この名前は、すでに汎用の連鎖アニメーションが完成したという意味ではありません。現在のANSIデモと限定的なトレースを出発点に、その先の表現を考えています。詳しくは[歴史と開発思想](docs/history-ja.md)を参照してください。

CHARM-IIの復元・研究については、[noteの記事](https://note.com/noborutkhs/n/n0f07002d2c4f)でも紹介しています。
英語の記事は[Mediumの連載「1980s Real-Time OS」](https://medium.com/@noborutakahashi/series-1980s-real-time-os-fd24fc389274)で公開しています。
